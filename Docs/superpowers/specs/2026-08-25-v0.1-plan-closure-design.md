# HLSRemuxKit 0.1 Plan Closure Design

## Objective

Close every known gap between the 0.1 implementation and the original design. The completed package must preserve an existing output on failure, provide deterministic single-operation cancellation semantics, report specific errors, prove TS and fragmented-MP4 remuxing with real media on an iOS simulator, and describe the bundled binary versions accurately.

## Scope

This work includes:

- Transactional output replacement.
- Explicit single-operation session ownership and cancellation behavior.
- Complete public error classification for the supported workflow.
- Unit coverage for file and state behavior.
- Real H.264/AAC TS and fragmented-MP4 fixtures.
- iOS simulator integration tests that inspect output tracks.
- Build-script integration and documentation corrections.

It does not add transcoding, remote HLS downloads, DRM support, background execution, multi-operation concurrency on one remuxer, x86_64 simulator binaries, or automated physical-device execution.

## Architecture

### Output Transaction

Each remux operation creates a uniquely named temporary MP4 in the destination directory. FFmpeg writes only to that temporary URL. This keeps the temporary file and destination on the same filesystem so the final replacement can be atomic.

On success, the implementation verifies that the temporary output exists, then replaces or moves it to the requested destination. If FFmpeg fails, the task is cancelled, the output is missing, or final installation fails, only the temporary file is removed. Any pre-existing destination remains untouched until successful installation.

The file lifecycle will live in a small internal component that accepts a `FileManager`. Its behavior can therefore be tested on macOS without importing FFmpegKit.

### Operation State

One `HLSRemuxer` supports at most one active operation. A second call made while an operation is starting or running fails with a dedicated `operationInProgress` error. Callers that need parallel remuxes may create separate `HLSRemuxer` instances.

The internal state distinguishes idle, starting, running, and cancellation-requested states. Task cancellation or `cancel()` records the cancellation request even if FFmpeg has not returned a session yet. When a session subsequently becomes available, it is cancelled immediately. Completion clears state only when it belongs to the same operation identifier, preventing an older callback from clearing newer state.

The state machine will be isolated behind a lock-protected internal type. Unit tests will exercise state transitions using operation identifiers and cancellation closures, without requiring an FFmpegKit session.

### Error Semantics

The public error cases will have these meanings:

- `inputMissing`: the local input URL does not exist.
- `outputParentUnavailable`: the destination directory cannot be created.
- `operationInProgress`: the remuxer already owns an unfinished operation.
- `failed`: FFmpeg or final output installation failed, with diagnostic details.
- `cancelled`: explicit cancellation or Swift task cancellation ended the operation.
- `outputMissing`: FFmpeg reported success but did not create the temporary output.

Every case will have a stable localized description and direct unit or integration coverage. A missing successful output must use `outputMissing`, not the generic `failed` case.

## Execution Flow

1. Reserve a new operation identifier. Reject the call if another operation is active.
2. Validate that the local input exists.
3. Create the output parent directory.
4. Allocate a unique temporary output URL in that directory.
5. Start FFmpeg with arguments targeting the temporary URL.
6. Register the returned session with the same operation identifier. If cancellation was already requested, cancel it immediately.
7. Forward optional FFmpeg statistics to the caller.
8. On successful FFmpeg completion, require the temporary output to exist and atomically install it at the destination.
9. On cancellation or failure, delete the temporary output and retain any old destination.
10. Clear the operation state only if the completing identifier still owns it.

## Media Fixtures And Integration Tests

The repository will include compact, deterministic fixtures suitable for source control:

- A short MPEG-TS file containing one H.264 video stream and one AAC audio stream.
- A local fragmented-MP4 HLS playlist, initialization segment, and media segment containing H.264 and AAC.

An iOS XCTest host will call both public remux methods against copied fixture files. Each successful test will assert that the MP4 exists, has nonzero size, and exposes at least one video and one audio track through AVFoundation. Additional integration cases will verify cancellation cleanup and preservation of an existing destination when the input is invalid.

The automated target is an available Apple Silicon iOS simulator because the bundled frameworks contain only arm64 simulator and device slices. Physical-device execution remains a documented optional check; the build must not claim that it ran on a device when none was connected.

## Build And Validation

The validation entry point remains `Scripts/build-ios.sh`. It will:

1. Run macOS unit tests for command construction, output transactions, state transitions, and errors.
2. Type-check the arm64 iOS simulator and device slices.
3. Build and run the integration test host on an available arm64 iOS simulator.

If no compatible simulator runtime is installed, the script must fail with a clear prerequisite message rather than silently skipping integration tests. A separate documented option may run only the host tests and slice type checks for environments intentionally lacking a simulator.

## Documentation And Versioning

Documentation will consistently identify the vendor payload as FFmpegKitNext wrapper 8.1.1 with FFmpeg libraries 8.1.2. README validation claims will distinguish unit tests, compile checks, simulator integration tests, and optional physical-device checks. LGPL notices and the corresponding-source obligation remain visible.

## Acceptance Criteria

- A failed or cancelled remux never removes or modifies an existing destination.
- A successful remux atomically replaces an existing destination.
- A single remuxer rejects overlapping operations deterministically.
- Cancellation works before and after FFmpeg session registration.
- All public error cases are reachable and tested.
- Real TS and fragmented-MP4 inputs produce MP4 files with video and audio tracks on an arm64 iOS simulator.
- Host tests, both iOS slice checks, and simulator integration tests pass from the documented validation command.
- Documentation contains no conflicting wrapper or FFmpeg version claims.
